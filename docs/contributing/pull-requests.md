# Pull requests

Every change you make reaches `main` through a pull request (PR). You can't push to `main` directly.

PRs are squash-merged. When a PR is merged, GitHub squashes all of its commits into one commit on `main`. The repository is set up so that GitHub builds that commit's message from the PR title and the PR description. Commits are the change log, so you write your PR as though it were itself a commit.

## How a PR becomes a commit

| PR field | Becomes | Format |
| --- | --- | --- |
| Title | The commit header (first line) | A commit header. See [Commit messages](commit-messages.md). |
| Description | The commit body and footers | A commit body, followed by any footers. |

Because each PR is squashed, every PR lands on `main` as a single commit. There are no merge commits, and the history on `main` stays linear.

## Write the title

Write the PR title exactly as you would write the first line of a commit message:

```text
type[ref](scope)!: Description
```

* `type` and `scope` are strictly lowercase.
* `[ref]` is optional. Use it for an issue reference, such as `[#123]` or `[resolve #123]`. A `[skip ci]` field also goes in brackets here, after any issue reference, such as `chore[#123][skip ci](docs): ...`. See [Skip CI](#skip-ci).
* `(scope)` is optional, but use one when the change has a clear area.
* `!` is optional. Use it only for a breaking change.

The header follows [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/). The `[...]` fields between the type and the scope are this project's extension. They aren't part of the Conventional Commits specification.

For example:

```text
feat[resolve #123](read): Implement the read credential helper interface
```

[Commit messages](commit-messages.md) has the full rules for each part of the header.

### Don't add the PR number

When GitHub merges the PR, it adds the PR number to the end of the title in `()`. You don't type it yourself. If the PR above is #321, the commit on `main` starts with this line:

```text
feat[resolve #123](read): Implement the read credential helper interface (#321)
```

The PR number in `()` and the issue reference in `[]` both stay in the header. The PR number links the commit to its review. The issue reference links it to the issue.

## Write the description

Write the PR description as the body of a multi-line commit message. Explain what has changed on the branch and why. Then add any footers, such as `BREAKING CHANGE:` or `Co-Authored-By:`.

```text
broader description of what has changed on this branch.

Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
```

Everything in the description becomes part of the commit history on `main`.

## Close an issue

To close an issue when the PR is merged, put a closing keyword and the issue number in `[]` in the title:

```text
fix[close #123](ipc): Bounds check pw input string
```

GitHub closes the issue when the squashed commit, whose header contains the keyword, lands on `main`. See [Closing an issue](commit-messages.md#closing-an-issue) for the list of closing keywords.

If the PR only contributes to an issue and shouldn't close it, use the issue number without a keyword, such as `[#123]`. If the PR doesn't relate to an issue, leave the reference out.

For more about issue references, see [Commit messages](commit-messages.md) and GitHub's guide to [linking a pull request to an issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue).

## Mark a breaking change

A breaking change needs both parts:

* A `!` before the `:` in the PR title.
* A `BREAKING CHANGE:` footer in the PR description that explains why the change isn't backward compatible.

Title:

```text
feat(sdk)!: Stream encoded json in read command response
```

Description:

```text
Longer change description

BREAKING CHANGE: Why this change is not API backward compatible.

Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
```

From `v1.0.0`, a breaking change leads to a new major version. While the version is `0.x`, it leads to a new minor version instead. A PR that bumps the major version to `v2` or later must also add the matching suffix, such as `/v2`, to the module path in `go.mod` and to the import paths. See [Versioning and releases](versioning-and-releases.md#major-versions-and-the-go-module-path).

## Credit AI collaboration

If any code in the PR was generated by an AI agent, add a `Co-Authored-By:` footer for the agent at the end of the PR description. This is mandatory. Putting it in the description means the squashed commit on `main` carries it.

```text
Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
```

If the PR also has a `BREAKING CHANGE:` footer, put the `Co-Authored-By:` footer after it.

## Keep PRs small

The project uses trunk-based development. Branches are short-lived, and PRs are small and focused.

* Make one change per PR. The PR becomes one commit, and one entry in the change log.
* If the work is large, split it into several PRs that each make sense on their own.
* New or unfinished code that could change behaviour for users goes behind a feature flag read from an environment variable, off by default, so every commit on `main` is releasable.
* Keep your branch up to date by rebasing it on `main`. Don't merge `main` into your branch.

See [Git workflow](git-workflow.md) for rebasing and feature flags.

## Skip CI

In special cases, such as fixing a typo in the docs, you can add `[skip ci]` to the PR title, after any issue reference:

```text
chore[skip ci](docs): Fix typo in readme
```

Don't use it on a PR that should bump the version. If you think your PR is an exception, say so in the PR and the reviewers will decide. The title becomes the header of the squashed commit on `main`, so it would skip that commit's workflows on `main`. Read [Skipping CI](commit-messages.md#skipping-ci) before you use it.

## Open a PR from a fork

External contributors open PRs from a fork. The title and description rules on this page still apply. See [Working from a fork](git-workflow.md#working-from-a-fork).

## Automated changes

Dependabot and GitBook also make changes to the repository. You don't write these by hand. See [Commits made by tools](commit-messages.md#commits-made-by-tools) for their formats.

## Checklist

Before you ask for a review, check that:

* The title is a valid commit header, without the PR number.
* The description reads as a commit body, with any footers at the end.
* Any issue the PR closes is referenced in the title with a closing keyword.
* A breaking change has both `!` in the title and a `BREAKING CHANGE:` footer.
* A PR that bumps the major version to `v2` or later also adds the matching suffix, such as `/v2`, to the module path in `go.mod` and to the import paths.
* The title doesn't contain `[skip ci]` if the PR should bump the version, unless the reviewers agree to an exception.
* The description ends with a `Co-Authored-By:` footer if the PR includes AI-generated code.
* The PR makes one focused change, and the branch is rebased on `main`.
